# AGENTS.md — GART Media

Этот файл содержит постоянные инструкции для Codex и других coding-агентов, работающих в репозитории GART Media.

## 1. Назначение проекта

GART Media — внутренняя медиасистема GART для хранения, каталогизации, поиска и повторного использования фотографий, видео, рендеров, AI-генераций, документов, производственных файлов и связанных материалов.

Система должна поддерживать текущую ручную файловую архитектуру и в будущем интегрироваться с Telegram, Google Drive / другим хранилищем, AI-классификацией и сайтом GART.

## 2. Главные архитектурные принципы

Не меняй эти принципы без явного объяснения причины и последствий миграции.

### 2.1 Один физический файл — одно основное место хранения

Не создавай физические копии одного и того же файла только ради того, чтобы он одновременно относился к категориям «военный», «Коелга», «стекло», «для сайта», «для презентации» и т.п.

Такие свойства должны решаться через метаданные, теги, коллекции и Usage-связи.

### 2.2 Основные сущности

Минимальная модель должна учитывать:

- `Project` — клиентский проект / заказ.
- `MediaSet` — серия материалов: одна съёмка, серия рендеров, AI-сессия, рекламный материал, подборка референсов и т.д.
- `MediaAsset` — отдельный физический файл.
- `Folder` — физическое или логическое расположение.
- `Tag` — свободная или управляемая метка.
- `Collection` — логическая подборка без копирования файлов.
- `Provider` — подрядчик / поставщик.
- `IngestBatch` — одна операция импорта.
- `VersionGroup` / `versionOf` — связь версий одного актива.
- `Usage` — где используется файл: сайт, презентация, соцсети и т.д.
- `AuditLog` — история действий.

Рекомендуемые связи:

- Project 1:N MediaSet
- MediaSet 1:N MediaAsset
- MediaAsset N:M Tag
- MediaAsset N:M Collection
- Provider 1:N MediaSet
- MediaAsset может ссылаться на предыдущую / базовую версию
- MediaAsset может иметь несколько Usage-записей

### 2.3 MediaSet — ключевая единица организации

Типы серий:

- `REAL` — съёмка реализованного объекта
- `SHOOT` — предметная / техническая съёмка
- `RENDER` — серия рендеров
- `AI` — серия AI-генераций
- `CONTENT` — рекламный контент
- `SUP` — материалы подрядчика
- `REF` — внешняя подборка / референсы
- `OTHER` — прочее

Рекомендуемое имя папки серии:

`YYYY-MM-DD_ТИП-НОМЕР_Короткое_название`

Примеры:

- `2026-09-03_REAL-0042_Иванов`
- `2026-09-04_SHOOT-0018_Титановые_буквы_блики`
- `2026-09-04_RENDER-0014_Лампада_LP014`
- `2026-09-04_AI-0031_Военный_комплекс_стекло`

## 3. Роли файлов внутри серии

Поддерживай следующие роли:

- `ORIGINAL` — оригинал, никогда не перезаписывается молча.
- `WORKING` — рабочая / промежуточная версия.
- `SELECT` — отобранный материал.
- `MASTER` — финальный высококачественный мастер.
- `EXPORT` — производная версия для сайта, соцсетей, Telegram, презентаций и т.п.
- `OLD_VERSION` — старая версия.

Не используй хаотичные имена вроде `final_final_v2_new` как единственный механизм версий.

## 4. Источник и права

Обязательное поле `sourceType` должно поддерживать:

- `GART`
- `CLIENT`
- `CONTRACTOR`
- `AI`
- `EXTERNAL`
- `UNKNOWN`

Не смешивай чужие работы, материалы подрядчиков и AI-генерации с реальными работами GART.

Отдельно храни права и допуски:

- `clientShowAllowed`
- `websiteAllowed`
- `presentationAllowed`
- `socialAllowed`
- `copyrightStatus`
- `creator`
- `sourceUrl`
- `rightsNotes`

Для `EXTERNAL` публикация от имени GART по умолчанию запрещена, пока право не подтверждено.

## 5. Файловое хранилище и код приложения

Код приложения и реальные пользовательские файлы должны храниться отдельно.

Пример:

- Код: `D:\GART_MEDIA_APP`
- Данные: `D:\GART_FILES`

Никогда не помещай реальные фото, видео, клиентские документы, рабочие архивы и пользовательское хранилище внутрь Git-репозитория приложения.

Используй переменную окружения, например:

`MEDIA_STORAGE_PATH=D:\GART_FILES`

## 6. StorageProvider

Доступ к файлам должен идти через абстракцию `StorageProvider`.

Для MVP реализуй `LocalStorageProvider`.

Архитектура должна позволять позже добавить:

- Google Drive
- S3-compatible storage
- Cloudflare R2
- NAS / MinIO

Не зашивай локальные пути по всему приложению.

## 7. База данных

Для MVP используй SQLite.

Допустимо Prisma или Drizzle, если нет сильной причины выбрать другое.

Не используй mock-данные вместо реальной SQLite-базы там, где по задаче нужна рабочая система.

Архитектура должна позволять миграцию на PostgreSQL в будущем без полной переделки доменной модели.

## 8. Импорт файлов

Ingest должен быть отдельным процессом.

При загрузке файлов приложение должно уметь:

1. принять один или много файлов;
2. создать или выбрать MediaSet;
3. назначить источник;
4. применить общие метаданные к пачке;
5. безопасно сохранить оригинал;
6. посчитать SHA-256 checksum;
7. проверить точные дубли;
8. сгенерировать thumbnail / proxy, если формат поддерживается;
9. создать MediaAsset в БД;
10. записать AuditLog;
11. сообщить пользователю итог импорта.

Каналы ingest в будущем:

- web upload
- `00_ВХОДЯЩИЕ`
- Telegram bot
- Google Drive / другое хранилище

## 9. Дубликаты

Точные дубли определяй по содержимому, а не только по имени файла.

Для этого используй SHA-256.

При совпадении не создавай молча вторую физическую копию.

Предложи пользователю:

- использовать существующий актив;
- пропустить импорт;
- сохранить отдельную копию только если это осознанно необходимо.

## 10. Оригиналы и безопасность данных

Никогда не перезаписывай оригинал без явного пользовательского действия.

Любые операции удаления должны идти через Trash.

Минимальный безопасный сценарий:

`Delete -> Trash -> Restore или отдельное окончательное удаление`

В первой версии лучше избегать необратимого физического удаления по умолчанию.

## 11. Перемещение, Rescan и Relink

Если файл перемещён через GART Media, обновляй путь в БД.

Пользователь может иногда перемещать файлы через Windows Проводник, поэтому приложение должно предусматривать:

- `Rescan`
- `Missing files`
- `Relink`
- обнаружение новых файлов

Не проектируй систему так, будто путь в БД никогда не может измениться вне приложения.

## 12. Thumbnails и производные файлы

Оригинал не должен изменяться при генерации превью.

Thumbnails, proxies, cache и временные файлы должны храниться отдельно от оригиналов и не попадать в Git.

Для MVP приоритет:

- JPG
- PNG
- WEBP

Видео, PDF, PSD, BLEND и другие форматы можно сначала хранить без полноценного превью, если реализация превью усложняет MVP.

## 13. Метаданные

Структурированные поля важнее свободных тегов для критических признаков.

Поддерживай как минимум:

- sourceType
- contentType
- fileRole
- projectId
- mediaSetId
- providerId
- status
- captureDate
- installationYear
- location
- creator
- copyrightStatus
- publication flags

Таксономические поля / теги:

- материал
- элемент
- тема / стиль
- процесс
- произвольные теги

База данных — главный источник метаданных.

Архитектура должна позволять в будущем экспортировать безопасную часть метаданных в XMP / IPTC / sidecar.

## 14. Коллекции

Collections — виртуальные подборки без физического копирования файлов.

Примеры:

- Для сайта / Военные комплексы
- Презентация / Белый мрамор
- Соцсети / Идеи на сентябрь
- Клиенту / Варианты лампад
- Лучшие реализованные работы 2026

Удаление MediaAsset из Collection не должно удалять физический файл.

В будущем можно реализовать Smart Collections по правилам метаданных.

## 15. Git

Git используется для кода приложения, а не для пользовательской медиатеки.

Обязательно исключай через `.gitignore`:

- `node_modules`
- `.env*` с секретами
- пользовательские БД с реальными данными
- thumbnails
- cache
- logs
- временные файлы
- локальное media storage
- реальные фото и видео

Перед крупными изменениями делай commit стабильного состояния.

После успешно завершённого этапа делай понятный commit.

Не выполняй destructive Git-команды без явной необходимости.

Не удаляй чужие несвязанные изменения пользователя.

## 16. Рабочий цикл Codex

Для каждой существенной задачи работай так:

1. Прочитай задачу и относящиеся к ней документы.
2. Проверь текущую реализацию до внесения изменений.
3. Если задача крупная, разбей её на небольшие этапы.
4. Перед крупным изменением сохрани стабильную точку Git, если это уместно.
5. Реализуй минимально достаточное изменение.
6. Запусти приложение / build / typecheck / lint / тесты.
7. Исправь обнаруженные ошибки.
8. Проверь основной пользовательский сценарий.
9. Кратко зафиксируй, что изменено и что ещё не сделано.
10. После стабильного результата сделай commit, если это часть текущего workflow.

Не ограничивайся фразой «код написан» — проверяй результат.

## 17. Тестирование

После изменений проверяй как минимум релевантные сценарии.

Для файловой части особенно важны:

- загрузка одного файла;
- batch upload;
- duplicate upload;
- создание папки;
- переименование;
- перемещение;
- перезапуск приложения;
- сохранность БД;
- thumbnails;
- Trash / Restore;
- missing file / relink, когда эта функция появится.

Если тестов ещё нет, добавляй их постепенно для критической бизнес-логики.

## 18. UI

Приложение desktop-first.

Основной layout:

- слева — дерево папок;
- сверху — поиск, upload, фильтры, переключение вида;
- в центре — gallery/list;
- справа — properties panel.

Приоритет — удобство реальной работы с большим количеством файлов, а не декоративные эффекты.

Не делай интерфейс перегруженным.

## 19. Производительность

Проектируй с расчётом как минимум на:

- 50 000 MediaAsset;
- тысячи папок;
- десятки тысяч связей тегов;
- lazy loading thumbnails;
- pagination / infinite scroll;
- индексы БД по основным полям поиска и фильтрации.

## 20. Что пока не нужно реализовывать без отдельной задачи

Не добавляй преждевременно:

- Telegram bot
- Google Drive API
- S3
- AI recognition
- facial recognition
- OCR
- сложное video transcoding
- автоматическую публикацию на сайт
- сложную многопользовательскую систему

Архитектура должна позволять это позже, но MVP не должен разрастаться без необходимости.

## 21. Нельзя менять без объяснения

Без явного объяснения и согласования не меняй:

- модель `Project -> MediaSet -> MediaAsset`;
- правило «один физический файл — один дом»;
- разделение Project / GART Content / Contractor / External Reference;
- роли Original / Working / Select / Master / Export;
- `sourceType`;
- отдельные права website / presentation / social / client-show;
- Tags + Collections вместо копирования файлов по категориям;
- checksum-дедупликацию;
- StorageProvider abstraction;
- отдельное хранение кода и пользовательских файлов.

Если считаешь, что одно из этих решений мешает реализации, сначала объясни проблему, предложи альтернативу и последствия миграции.
