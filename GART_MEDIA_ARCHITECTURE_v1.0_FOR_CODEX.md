# GART Media — зафиксированная файловая архитектура v1.0

## 1. Базовая модель

Физическая файловая система отвечает только за стабильное место хранения.
Семантика не должна кодироваться десятками вложенных папок.

Основные сущности будущего приложения:

- `Folder` — физическое/логическое расположение.
- `Project` — клиентский заказ.
- `MediaSet` — серия: одна съёмка, серия рендеров, AI-сессия, рекламный материал, подборка референсов и т.д.
- `MediaAsset` — отдельный файл.
- `Tag` — гибкая метка.
- `Collection` — логическая подборка без копирования файлов.
- `Provider` — подрядчик/поставщик.
- `IngestBatch` — сессия импорта файлов.
- `VersionGroup` / `versionOf` — связь версий одного актива.
- `Usage` — где файл используется: сайт, презентация, соцсети и т.д.
- `AuditLog` — история действий.

Связи:
- Project 1:N MediaSet
- MediaSet 1:N MediaAsset
- MediaAsset N:M Tag
- MediaAsset N:M Collection
- Provider 1:N MediaSet
- MediaAsset может иметь `versionOf` / VersionGroup
- MediaAsset может иметь N Usage-записей

## 2. Главное правило

Один файл имеет одно физическое место хранения.
Папки не должны использоваться вместо тегов.

Например файл физически:
`02_КОНТЕНТ_GART/01_РЕАЛИЗОВАННЫЕ_ОБЪЕКТЫ/2026/2026-09-03_REAL-0042_Иванов/04_МАСТЕРА/IMG_1234.jpg`

Метаданные:
- source = GART
- contentType = RealizedObject
- material = Коелга
- elements = [Стекло, Титановые буквы, Медали]
- theme = Военный
- websiteAllowed = true
- presentationAllowed = true
- socialAllowed = true

Файл не копируется физически в папки "Стекло", "Военные", "Буквы", "Сайт".

## 3. MediaSet

MediaSet — ключевая сущность.

Примеры:
- REAL — съёмка реализованного объекта
- SHOOT — предметная/техническая съёмка
- RENDER — серия рендеров
- AI — серия AI-генераций
- CONTENT — рекламный ролик/контент
- SUP — материалы подрядчика
- REF — внешняя подборка
- OTHER — прочее

Рекомендуемое имя папки:
`YYYY-MM-DD_ТИП-НОМЕР_Короткое_название`

## 4. Роли файлов внутри MediaSet

- ORIGINAL — оригинал; никогда не перезаписывается.
- WORKING — рабочая/промежуточная версия.
- SELECT — отобранный материал.
- MASTER — финальный высококачественный мастер.
- EXPORT — производная версия для конкретного канала.
- OLD_VERSION — старая версия.

## 5. Источник

Обязательное поле `sourceType`:
- GART
- CLIENT
- CONTRACTOR
- AI
- EXTERNAL
- UNKNOWN

Чужие работы и материалы подрядчиков должны быть явно отделены от собственных работ GART.

## 6. Права/допуски

Не объединять право "показывать" с правом "публиковать".

Поля:
- clientShowAllowed
- websiteAllowed
- presentationAllowed
- socialAllowed
- copyrightStatus
- creator
- sourceUrl
- rightsNotes

Для EXTERNAL по умолчанию публикация от имени GART запрещена, пока право не подтверждено.

## 7. Метаданные и теги

Структурированные поля:
- sourceType
- contentType
- fileRole
- projectId
- mediaSetId
- providerId
- status
- captureDate
- installationYear
- location
- creator
- copyrightStatus
- publication flags

Таксономические поля/теги:
- material: Коелга, габбро-диабаз, пероксенит...
- element: стекло, лампада, ваза, медаль, крест, буквы...
- theme/style: военный, семейный, современный, минимализм...
- process: гравировка, фотопечать, монтаж...
- arbitraryTags

База данных является основной системой метаданных.
Для переносимости архитектура должна позволять экспортировать безопасную часть метаданных в XMP/IPTC или sidecar-файлы.

## 8. Коллекции

Collections — виртуальные подборки без физического копирования.

Примеры:
- Для сайта / Военные комплексы
- Презентация / Белый мрамор
- Соцсети / Идеи на сентябрь
- Клиенту / Варианты лампад
- Лучшие реализованные работы 2026

Удаление файла из Collection не удаляет физический файл.

Smart Collections должны уметь автоматически собирать файлы по правилам тегов/метаданных.

## 9. Версии

Не использовать `final_final_v2_new`.

Приложение должно:
- связывать версии одного актива;
- показывать текущую/главную версию;
- сохранять старые версии;
- позволять сравнение/откат в будущем.

## 10. Ingest

При загрузке приложение должно уметь:
- принять один или много файлов;
- создать/выбрать MediaSet;
- определить источник;
- применить общие метаданные к пачке;
- безопасно скопировать файлы;
- посчитать checksum SHA-256;
- найти точные дубли;
- сгенерировать thumbnails/proxies;
- записать AuditLog;
- после успешного импорта подтвердить пользователю результат.

Каналы ingest в будущем:
- web upload
- локальная папка / 00_ВХОДЯЩИЕ
- Telegram bot
- Google Drive / другое хранилище

## 11. Дубликаты

Точные дубли определять по содержимому (SHA-256), а не только по имени.
При совпадении:
- не создавать молча вторую копию;
- показать существующий актив;
- предложить связать/пропустить/сохранить отдельно при осознанной необходимости.

## 12. Перемещение файлов

Если пользователь перемещает файл через GART Media, приложение обновляет путь в БД.
Если пользователь переместил файл через Проводник, нужен:
- Rescan;
- поиск missing assets;
- Relink;
- обнаружение новых файлов.

Приложение не должно считать карточку единственным существованием файла.

## 13. Backup ≠ Archive ≠ Sync

Storage, backup и archive — отдельные функции.
Минимальная целевая стратегия для важных данных:
- рабочая копия;
- отдельная локальная резервная копия;
- одна off-site/облачная копия.

Удаление в приложении:
- сначала Trash;
- восстановление;
- окончательное физическое удаление только отдельным явным действием.

## 14. Что Codex НЕ должен менять без причины

- верхнеуровневые категории v1.0;
- концепцию MediaSet;
- правило "один физический файл — один дом";
- отделение Project / Content / Contractor / External Reference;
- разделение Original / Working / Select / Master / Export;
- систему sourceType;
- отдельные права website/presentation/social/client-show;
- Tags + Collections вместо копирования файлов по категориям;
- checksum-дедупликацию;
- StorageProvider abstraction.

Любое изменение этих принципов сначала должно быть объяснено как архитектурная миграция.
